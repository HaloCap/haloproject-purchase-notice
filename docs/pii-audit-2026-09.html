3.2 .githooks/pii_guard.py + .githooks/pre-commit

零依賴（只用 Python 3 標準函式庫，沒有 pip、沒有 husky、沒有 pre-commit framework）。 三個設計上的堅持：

① 看的是暫存區，不是工作目錄

用 git show :<path> 讀內容。會被 commit 的是暫存區那一份， 守門就該看那一份——不然 git add 之後再改檔案就能繞過。

② 表格偵測刻意不只看副檔名

對每個文字檔嗅探分隔符號一致性。無副檔名的 CSV 一樣會被認出來—— 這條規則存在的理由就是第一節那個檔案。超過 50 列即攔截。

③ 命中一律遮蔽後才輸出

守門的錯誤訊息會進 terminal、進 CI log、進截圖。 如果它照抄命中的個資，它本身就是第二次外洩。

④ 母體斷言 —— 這條是重點

一支只比差集的守門，在掃描目標變空時會「誠實地回報通過」。 它沒有說謊，它只是瞎了——而且瞎掉的樣子跟健康的樣子一模一樣，都是綠燈。

所以這支守門每一次執行都先驗證自己，三項任一不成立就 exit 1：

斷言失敗時的訊息它防的是什麼
規則數 ≥ 7規則母體縮小了有人「順手清理」刪掉了規則
自我測試全數命中偵測器壞了正規表示式被改壞，靜靜不再命中
暫存檔案數 == 實際處理數視野縮小了有檔案被靜默跳過（讀不到、編碼錯誤）卻仍放行

另外，pre-commit 那層 shell 也拒絕在找不到 python3 或找不到守門檔時「假裝通過」——守門跑不起來就不該算通過。

  1. 一個文字檔，內含一組虛構的手機號碼

另一個方向也驗了：守門不會誤傷自己

守門的原始碼裡有 token、secret、password 這些字， 還有各種號碼樣式的正規表示式。天真的寫法會讓守門攔下自己， 而通常的解法是加一條「路徑白名單」放自己過——但白名單正是守門變瞎的第一步。

這裡改用兩個手段避開：密鑰規則要求「有引號、8 字元以上的值」才算命中； 自我測試的假資料用字串拼接組出來，字面上不出現完整樣式。 所以沒有任何路徑豁免，守門掃自己時一樣是全額檢查——實測 3 個檔案全過。

已知的誤判方向（拿真實資料校準過）

我拿 lixin 那份 129 列的事故佐證 CSV 當外部樣本跑過守門。 結果：正確攔下（表格超列），但另外有 5 筆 CREDIT_CARD 誤判—— 那些是很長的數字型 lead ID，剛好通過了 Luhn 檢查（約 1/10 機率，符合預期）。

這是刻意選的方向：守門寧可多攔，不可漏放。 誤判的成本是打一次 --no-verify，漏放的成本是一份公開的名單。 但知道它會在「長數字 ID」上吵，可以省下未來 debug 的時間。

決策 1 · 這個 repo 該不該刪 我的判斷：先不要刪

CTO 的建議是直接刪，理由是 90 天 0 commit、112 行、已無活動。 我不同意，而且理由不是感情因素，是指標選錯了。

先更正兩個數字：實際是 27 個檔案、1,029 行（112 行是 scripts.js 單一檔案的行數），最後活動距今約 190 天而非 90 天。 如果刪除決策是建立在「只有 112 行」上，那個前提是錯的。

更重要的是：這不是程式碼，是上線中的客服內容。 它是一頁「購買須知＋客製化需求表單」。一頁靜態說明頁 190 天沒有 commit， 這是正常且健康的——說明沒變，頁面就不該變。 用 commit 頻率去判斷一份說明文件是否還活著，等於用「這份合約多久沒改」 去判斷它是否還有效。

真正該問的問題不是「它還有沒有在動」，是「還有沒有人在用」。 而那個答案不在磁碟上。

我查過了：整個 halo 工作區沒有任何一個地方連向 halocap.github.io/haloproject-purchase-notice （grep -rn 'halocap.github.io' 零命中）。 但這只證明程式碼裡沒有連結。這種網址最可能待的地方， 剛好全部都不在版控裡。

刪之前必須先確認的五件事（由最可能到最不可能）

  1. IG bot 的自動回覆規則。 halo-ig-bot 的 rules 資料表——關鍵字觸發 DM 最常回的就是 「購買須知」這種連結。這是最可能的藏匿處，先查這個。
  2. EasyStore 後台。商品描述、頁面、FAQ 裡有沒有貼這個網址。 要去 ES 後台搜 halocap.github.io，repo 裡搜不到。
  3. LINE 官方帳號。圖文選單、自動回覆、歡迎訊息。
  4. GitHub Pages 流量。Repo → Insights → Traffic。 只留 14 天——要看就現在看， 拖過兩週就永遠不知道它有沒有人在用了。
  5. IG 個人檔案連結、限動精選、舊貼文裡的短網址。

我建議的階梯（成本由低到高）

  1. 現在就做，零成本：把 repo 設成 archived。 變唯讀、GitHub 明確標示「不再維護」、Pages 繼續服務（archived repo 的 Pages 不會停）。 解決了「看起來像沒人管的空殼」的形象問題，而且不會讓任何人的連結 404。 隨時可以解除。這一步不需要先查上面五件事。
  2. 順手做：把 README 補成三行（這是什麼、線上網址、內容在 develop）， 或把 develop 併回 main。目前打開 repo 首頁是空的。
  3. 要收掉的話：先搬再轉址，最後才刪。 內容搬到 haloepoch.com 對應頁面（那兩頁本來就存在，這頁自己還連過去）， Pages 留一個 meta refresh 轉址跑三個月，確認流量歸零再刪。

一句話：直接刪省下的是 0 元（public repo 與 Pages 都免費）， 賠上的是一個客戶點下去會 404 的連結。這筆帳不划算。 Archive 拿到了刪除想要的全部好處（明確標示不維護、不再是活躍門面）， 卻沒有付出任何代價。

決策 3 · 要輪替哪把 token

沒有。這是一個乾淨的否定答案。

決策 4 · 根目錄 CLAUDE.md 要不要修

我沒有改它——那是跨 repo 的共用文件，不該由一次單 repo 的稽核順手改掉。但它現在是錯的， 而且錯的方式有風險：它把另一個客戶（lixin）的專案結構寫進了 Halo 自家 repo 的描述裡。

加上今天已經查證的「描述了 3 個不存在的 repo、漏掉 11 個存在的」， 這份文件目前的準確率低到不該被當成事實來源。 對 AI 助理來說這特別危險——它們會照著文件去找東西， 找不到就自己補一個合理的說法，於是錯誤會被複製到下一份文件裡。 這次的 facebook_leads_full_20260131.csv 就是這樣的產物： 一個從未存在、但被反覆引用的檔名。

建議：把 haloproject-purchase-notice 那段整段換成一行事實—— 「靜態購買須知頁，Jekyll + GitHub Pages，來源分支 develop，無後端、無資料檔」。 lixin 的部分要不要另外記錄是另一個問題，但它不該記在 Halo 的架構圖裡。

決策 5 · 那份 14 MB 名單的保管

目前狀態是安全的（PRIVATE repo、未追蹤、已被 ignore、從未提交）。 但它只靠一行 .gitignore 撐著，而且躺在 repo 工作目錄的正中央。

成本最低的補強，照效益排序：

  1. 把它移出 repo 目錄（例如 ~/private-data/）。 一個檔案不在 repo 底下，就沒有任何 git 操作能意外收錄它。這一步最有效。
  2. 把同一支守門裝到 lixin 那個 repo。.gitignore 只擋住「你沒有 -f」的情況； 守門連 git add -f 之後也還會攔。
  3. 訂一個保存期限。一份 2026-04 的完整名單，到今天（2026-09）還需要留在筆電上嗎？ 不再需要的個資，刪掉是最徹底的防護——沒有任何守門比「檔案不存在」更可靠。
  4. ~/Downloads 那兩份小的名單匯出檔，一併處理。
